## 一、分级口径（先看这节）

五组不是「严重度新五档」，而是**上线决策档**：同一档意味着「同样的动作时点」。判定按三轴：

| 轴 | 含义 |
|---|---|
| **后果** | 落到什么资产上：密钥/长期凭据、审计链完整性、身份真实性、合规义务、标准契约 > 跨租户可用性 > 单租户可用性/可观测性 > 开发者体验 |
| **前提门槛** | 触发它需要什么：无前提 / 一次常规运维动作 / 一次配置笔误 / 攻击者能左右外部输入 / 需真实 Postgres 才能定论 |
| **修法代价** | 一行改 .gitignore 也算「必须马上做」；需要 ADR 裁定、改跨后端契约、动迁移回退语义的，天然排后面 |

**本项目的既有升档规则仍然生效**（`docs/issues/README.md` §「严重度怎么定」）：
**失败是静默的**（报成功、计数为 0、退出码 0、只有 Debug 日志）一律往上抬。
所以本表里「后果满级 + 前提较高」的条目（如 `Z14-3`、`Z21-2`）之所以进 T1，
正是因为它的失败**完全静默**，而不是因为前提低。

| 组 | 名称 | 定义（动作时点） | 判据 |
|---|---|---|---|
| **T1** | **不修不能上线** | 打 `v0.0.0-rc.4` 之前必须收掉 | 后果落在**不可逆资产/不可回溯义务**上：长期密钥材料、审计链防篡改、身份伪造、合规/归属义务、OIDC 标准 MUST；且**修法小、无裁定依赖** |
| **T2** | **首发窗口必修** | rc.4 之后、**首个正式版本之前**（≈1–2 周） | 明确安全后果或契约破坏，但后果有界、或有明确前置条件；含**刚修完的 P0/P1 的回归防线** |
| **T3** | **首个补丁** | 上线后 1–2 个迭代（**月内**） | 可用性/可观测性有界缺陷、运维安全默认值、CI 门禁空转；不修不会放大成事故，但会持续磨损检测能力 |
| **T4** | **一个季度内排期** | 下次常规排期 | 需要裁定或架构改动，或只在真实 Postgres 上才能定论，或纯 CI/供应链卫生 |
| **T5** | **上线数月后** | 可以拖 | 规范细节、需先有裁定、影响在源侧实现或纯一致性；不改变安全姿态 |

> **注意**：T1 里近一半属于「**修法一行 vs 泄漏满级**」的尾部风险（`Z12-1`、`Z13-1`、`Z13V-1`、`Z19-1 / Z19V-1`）。
> 这类条目的正确处置不是「评估它会不会发生」，而是**因为修复便宜到没有理由接受尾部**。

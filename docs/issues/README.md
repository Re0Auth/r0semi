# 问题寄存器（Issue Register）

> **这一份是「要修的东西」的唯一清单，按严重度排，不按轮次排。**
> 同一个洞在哪一轮被发现，不影响怎么修；轮次只作为一个字段保留，方便回溯证据。
>
> **最新版本口径**：本寄存器已收录到**第九轮独立审计**（[`docs/security-audit-9.md`](../security-audit-9.md)，
> 只读 HEAD 生产代码、不引用前几轮结论）。第九轮之前的条目来自 `_fragments/rounds2-4.md`、
> `round5.md`、`round6.md`、`round7.md`。数字由 `_fragments/_counts.json` 自动给出，不要手抄。

## 为什么有这个文件夹

前六轮的产物是按**轮次**组织的（`docs/security-audit-2.md`、`docs/security-audit-5.md`、
`AUDIT-ISSUES.md`、`docs/audit-6/**`、`docs/audit-7/**`）。
"修哪一条"从来不是按轮次决定的，所以这里把它翻过来：**一个洞一条，落在一个严重度文件里**。

## 生成链（可重跑，不要手改生成文件）

```sh
node docs/issues/_fragments/_extract_round9.mjs   # 报告 -> _fragments/round9.md
node docs/issues/_fragments/_merge.mjs            # 全部片段 -> P0..P3/fixed/_counts.json
```

- `_extract_round9.mjs` 把第九轮报告的高/中/低/信息映射到寄存器的 P0/P1/P2/P3，并把
  §5 的内部去重写成 `合并` 注记。Low/Info 标题保留报告原文（英文），Medium 为人工中文摘要。
- `_merge.mjs` 按「轮次越晚越权威」合并，同 ID 只保留一条；`ALIAS` 表落实同机制合并；
  结束时会打印并向 `_counts.json` 写入**在册 / OPEN** 数量。
- 额外的手工片段：[`_fragments/conformance.md`](_fragments/conformance.md)（OIDF 一致性套件门禁的
  4 条已知缺口，来自 `docs/conformance.md`）。
- **生成文件**：`P0-blockers.md`、`P1-high.md`、`P2-medium.md`、`P3-low.md`、`fixed.md`、
  `not-doing.md` 的生成区、`_counts.json`。`P2-triage.md` 与本文是**手写**的。

## 严重度怎么定

沿用本项目的口径（`docs/audit-7/BRIEF.md` §6，与前几轮一致）：

- **P0 阻断**：未认证的鉴权绕过、跨账号读写、凭据泄露、匿名可触发的 DoS、数据丢失/不可恢复、
  发布产物本身不安全；**失败是静默的** ⇒ 升档。
- **P1 高**：低门槛前提（一次登录、一个公开 client）即可扩大权限或读他人数据；
  或生产环境下的稳定性/正确性缺陷。**失败是静默的** ⇒ 升档。
- **P2 中**：前提较高，或影响有界但确定。
- **P3 低/提示**：加固、纵深防御、文档与实现不一致、可维护性。

> **「失败是静默的」是本项目升档的主要依据**：报成功、计数为 0、退出码 0、无日志、
> 或者只有 `Debug` 级别日志 —— 这些一律往上抬一档。

## 一条问题长什么样

**P0/P1 用写实格式**（一条一节，必须能独立看懂）：

```markdown
### <ID> <一句话标题>
- **轮次**：第 6 轮（G-1）
- **位置**：`internal/store/memory/oidc.go:552-559`
- **影响**：<人话：攻击者/运维实际得到什么>
- **修法**：<最小改法；涉及裁定就写明是裁定>
- **状态**：OPEN | FIXED | DECIDED-NONGOAL
- **证据**：<探针名 / 命令 / file:line>
- **来源**：`<原始报告>:<行>`
```

**P2/P3 用表**（一行一条）：

```markdown
| ID | 严重度 | 问题 | 位置 | 状态 | 修法要点 | 轮次 |
|---|---|---|---|---|---|---|
```

## 维护规则

1. **一个洞一条，落在它最终的严重度文件里。** 严重度变了就**搬文件**，不要两处都留。
2. **发现重复就合并**，把另一个 ID 写进 ID 列或问题的「§5 合并」注记里。
3. **修好了**：把 `状态` 改成 `FIXED` 并写上修复的 commit；不要直接删——删掉就没法回答
   "这条当初为什么存在"。
4. **新增**：往对应严重度文件里加，并在 `_fragments/` 里注明来源轮次/报告；能自动抽取的
   写进 `_extract_*.mjs`。
5. **不要在这里重复 `not-doing.md` 里的条目**。

## 三条不变量

1. **不管第几轮发现，只要在 `HEAD` 上仍然存在，就得有归宿**（四份严重度文件或 `not-doing.md`）。
2. **每条必须有 `file:line` 或一条会失败的探针** —— 没有证据的条目不许进册。
3. **严重度以对抗性复核后的裁定为准**，不是以区域报告的自评为准
   （第七轮复核把 `Z10-1`/`Z10-2` 从 P2 降到 P3、把 `Z17-1` 从 P2 降到 P3、
   把 `Z18-1`/`Z10-3` 判为重报、把 `Z08-5` 从 P2 降到 P3）。

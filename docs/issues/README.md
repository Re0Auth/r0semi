# 问题寄存器（Issue Register）

> **这一份是「要修的东西」的唯一清单，按严重度排，不按轮次排。**
> 同一个洞在哪一轮被发现，不影响怎么修；轮次只作为一个字段保留，方便回溯证据。

## 为什么有这个文件夹

前六轮的产物是按**轮次**组织的（`docs/security-audit-2.md`、`docs/security-audit-5.md`、
`AUDIT-ISSUES.md`、`docs/audit-6/**`、`docs/audit-7/**`）。
"修哪一条"从来不是按轮次决定的，所以这里把它翻过来：**一个洞一条，落在一个严重度文件里**。

## 严重度怎么定

沿用本项目的口径（`docs/audit-7/BRIEF.md` §6，与前几轮一致）：

- **P0 阻断**：未认证的鉴权绕过、跨账号读写、凭据泄露、匿名可触发的 DoS、数据丢失/不可恢复、
  发布产物本身不安全；**失败是静默的** ⇒ 升档。
- **P1 高**：低门槛前提（一次登录、一个公开 client）即可扩大权限或读他人数据；
  或生产环境下的稳定性/正确性缺陷。**失败是静默的** ⇒ 升档。
- **P2 中**：前提较高，或影响有界但确定。
- **P3 低/提示**：加固、纵深防御、文档与实现不一致、可维护性。

> **「失败是静默的」是本项目升档的主要依据**：报成功、计数为 0、退出码 0、无日志、
> 或者只有 `Debug` 级别日志 —— 这些一律往上抬一档。

## 一条问题长什么样

**P0/P1 用写实格式**（一条一节，必须能独立看懂）：

```markdown
### <ID> <一句话标题>
- **轮次**：第 6 轮（G-1）
- **位置**：`internal/store/memory/oidc.go:552-559`
- **影响**：<人话：攻击者/运维实际得到什么>
- **修法**：<最小改法；涉及裁定就写明是裁定>
- **状态**：OPEN | FIXED | DECIDED-NONGOAL
- **证据**：<探针名 / 命令 / file:line>
- **来源**：`<原始报告>:<行>`
```

**P2/P3 用表**（一行一条）：

```markdown
| ID | 问题 | 位置 | 状态 | 修法要点 | 轮次 |
|---|---|---|---|---|---|
```

## 状态图例

| 状态 | 含义 |
|---|---|
| `OPEN` | 在 `HEAD` 上仍然存在，**要修** |
| `OPEN-PG` | 只有真实 Postgres 上才能定性（本机无库），需要在 CI 的 `postgres:16` 上跑成定论 |
| `DECIDED-NONGOAL` | 有意的取舍，见 `not-doing.md`；**不要当缺陷上报** |
| `FIXED` | 已修；保留在册只为溯源 |

## 维护规则

1. **一个洞一条，落在它最终的严重度文件里。** 严重度变了就**搬文件**，不要两处都留。
2. **发现重复就合并**，把另一个 ID 写进 `别名` 字段（例：`G-11 / 22-1 / Z18-1` 是同一机制）。
3. **修好了**：把 `状态` 改成 `FIXED` 并写上修复的 commit；不要直接删——删掉就没法回答
   "这条当初为什么存在"。
4. **新增**：往对应严重度文件里加，并在 `_fragments/` 里注明来源轮次/报告。
5. **不要在这里重复 `not-doing.md` 里的条目**。

## 本轮（第七轮）给这份寄存器定的三个不变量

1. **不管第几轮发现，只要在 `HEAD` 上仍然存在，就得有归宿**（四份严重度文件或 `not-doing.md`）。
2. **每条必须有 `file:line` 或一条会失败的探针** —— 没有证据的条目不许进册。
3. **严重度以对抗性复核后的裁定为准**，不是以区域报告的自评为准
   （第七轮复核把 `Z10-1`/`Z10-2` 从 P2 降到 P3、把 `Z17-1` 从 P2 降到 P3、
   把 `Z18-1`/`Z10-3` 判为重报、把 `Z08-5` 从 P2 降到 P3）。

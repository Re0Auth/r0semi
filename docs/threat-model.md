# r0semi 威胁模型与信任边界（v0.1）

> 状态：草案。本文档优先于代码，任何架构/协议决策都必须能在此文档中找到依据。

## 1. 项目定位

r0semi 是一个**凭据经纪（Credential Broker）**，而非纯 OAuth 授权服务器。

- 对上：接收玩家一次性托管的 TapTap `stoken`，用密码学手段保护。
- 对下：向下游工具签发受控、有时效、可撤销的令牌；下游**永远接触不到**原始 stoken。

核心契约：**stoken 的明文只在 r0semi 内部存在，且只在调用上游的瞬间存在。**

## 2. 资产分级

| 编号 | 资产 | 敏感度 | 备注 |
|---|---|---|---|
| A1 | 用户 TapTap `stoken` | 最高 | 长效、不可细粒度授权、泄露即账号沦陷 |
| A2 | Vault DEK / KMS KEK | 最高 | 保护 A1 的密钥 |
| A3 | 用户身份 / 成绩数据 | 高 | 个人数据，受合规约束 |
| A4 | r0semi 的 AT / RT / client_secret | 中高 | 短寿命、可撤销 |
| A5 | 审计日志 | 高 | 完整性要求（防篡改） |
| A6 | Vault 记录中的 `Identity` / `Meta`（`usr_` ↔ 数据源、上游 openid/unionid） | 中高 | **非密钥但属 PII，明文落盘**；需合规时纳入密文（见 §6.1） |

## 3. 信任边界

| 边界 | 说明 | 信任级别 |
|---|---|---|
| B1 玩家 ↔ r0semi | 托管 stoken 的时刻，明文传输一次 | 传输层加密，客户端不可信 |
| B2 下游客户端 ↔ Auth Server | 桌面/CLI/Web 均为 public client | **完全不可信**，无 client_secret |
| B3 Broker ↔ TapTap | 唯一有权接触 stoken 明文的路径 | 上游可信，但需端点白名单 |
| B4 应用 ↔ KMS/Vault | 密钥边界 | 密钥不可导出，解封需鉴权+审计 |
| B5 运营者 / 内部人员 | 最高权限 | **不受信任**，最小权限 + 全程审计 |

## 4. 风险形态：从独立风险到相关风险

公共托管不会凭空制造风险，而是改变风险的形态：

| | 现状（各工具各存一份） | r0semi 公共 Vault |
|---|---|---|
| 泄露点数量 | N | 1 |
| 单点沦陷影响面 | 该工具的用户 | 全体用户（相关失效） |
| 安全下限 | 最差工具决定 | r0semi 的 opsec 决定 |
| 下游持有 stoken | 是 | 否（只持有短寿命 AT） |

结论：以**相关性风险换取更高的安全下限**是被接受的权衡。前提是 r0semi 的安全实践显著优于社区平均水平。

## 5. 关键设计决策（ADR 摘要）

- **D1 公共托管**：为达到网络效应与采纳率，提供官方公共实例。（自托管作为可选附带能力保留。）
- **D2 永不返回 stoken**：任何 scope、任何 API 都不得返回 A1。下游获得的是数据型 API 或端点白名单内的代理结果。
- **D3 信封加密**：KEK 存于 KMS/HSM 且不可导出；每用户独立 DEK；每次解封都鉴权 + 审计。
- **D4 两层撤销**：下游撤销是纯本地的（只失效 r0semi 的 AT/RT）；上游撤销（作废全部 sessionToken）必须显式、在 UI 上明确警告，且**不保留**旋转后的新 token。见 §7。
- **D5 全局 Kill Switch**：存在一键级联注销全部上游凭据的能力，用于事故响应。

## 6. 密钥层级

```
KMS/HSM (KEK, 不可导出)
      └── 每用户 DEK (AES-256-GCM)
                └── stoken 密文 (落库)
```

- 数据库单独泄露 ⇒ 无法解密（KEK 在 KMS）。
- DEK 解封必须经由 Broker 身份，并写入审计。
- 明文 stoken 在内存中的生命周期最小化，用后立即擦除。

### 6.1 落盘时不加密的部分（PII 定性）

凭据记录里有两块**按设计不加密**，因为它们要在没有 KEK 的情况下可用：

| 字段 | 内容 | 定性 | 落盘泄露的后果 |
|---|---|---|---|
| `Identity{Subject, Provider}` | `usr_` + 数据源命名（如 `phigros.next-phi`） | **非密钥，但属个人数据** | 泄露“某人绑定了哪些游戏/数据源” |
| `Record.Meta` | 上游 openid / unionid / LeanCloud objectId | **非密钥，但属 PII** | 泄露上游身份标识，可与其它泄露关联 |

两者都是**明文**，`threat-model` 与代码注释（`vault.Identity`、`vault.Record.Meta`）均已如实标注。若部署的合规要求覆盖元数据，处置方式是把 `Meta` 一并纳入密文（它目前**只写不读**，改动面很小）。

同样，**下发令牌（`oauth.Store`）与上游令牌（绑定的 vault 记录）都不落明文**：前者按键 `sha256(value)` 查表，后者信封加密；绑定表本身只存元数据（`HasRefresh` / `Expiry` / `Version`）。

## 7. 撤销：本地撤销与上游撤销是两件事（已查证）

上游是 TapTap 内建账户（LeanCloud / TDS）体系。查证结论：

- `sessionToken` **每个用户在每个应用内唯一**，即民间所称的 "stoken"。它**长期有效，直到用户主动登出**。
- 服务端**没有**“登出”或“按会话撤销”接口。唯一能作废它的方式是
  `PUT /1.1/users/<objectId>/refreshSessionToken`：调用后**旧 sessionToken 立即失效，
  所有持有它的登录均收到 403**，并返回一个新的 sessionToken。
- 该接口可用**当前 sessionToken**（`X-LC-Session`）或应用 **Master Key** 调用。
- 修改密码后若开启“强制客户端重新登录”，也会重置 sessionToken。

因此上游**没有按客户端 / 会话粒度的撤销**。据此把撤销拆成两层：

| 层 | 触发 | 动作 | 影响 |
|---|---|---|---|
| **本地撤销**（默认） | 用户解除某个下游应用的授权 | 仅失效 r0semi 的 AT/RT | 只影响该下游应用 |
| **上游撤销**（显式、需警告） | 用户主动“作废全部” / 运营者 Kill Switch | 用持有的 sessionToken 调 `refreshSessionToken`，**丢弃返回的新 token** | 作废全部上游登录，**包括用户自己设备上的登录** |

关键设计约束：

1. **默认绝不调上游撤销**。调一次就会把用户自己的手机登录踢下线。
2. **不保留旋转后的新 token**。若保留，r0semi 等于静默劫持会话并把用户踢出，不可接受。
   故上游撤销后，vault 条目标记 dead、擦除 DEK，用户必须重新托管。
3. **不使用 Master Key**。当前 token 足以完成旋转；Master Key 权限过大，不应引入。
4. **补偿幂等性（I4）**：`refreshSessionToken` 本身不幂等，但把目标定义为“旧 token 已失效”
   就是幂等的——重试遇到 403 即视为达成目标（响应丢失导致的重复旋转无害，因为新 token 本就要丢弃）。
5. **被动失效检测**：任何上游调用返回 403 → 判定 stoken 已失效 → 标记条目 dead 并要求重新托管。

对 consent 文案的要求：任何会触及上游撤销的操作，必须明说“将导致你本机也需要重新登录”。

5. ~~TapTap OAuth2 设备码流程与 `sessionToken` 的关系~~ **已查证**（见 architecture.md §4.3）：
   设备码 → token → MAC 签名取账号 → LeanCloud `/users`（authData.taptap）→ **直接返回 sessionToken**。

在验证前，上游适配器按“行为显式、失败可见、可重试”设计。

## 9. 开放风险与治理

- **运营者信任**：公共实例的信任锚是运营方，需要透明度报告、warrant canary、第三方安全审计、密钥多人控制。
- **司法/合规**：PIPL（及可能的 GDPR）要求告知同意、最小化、可删除、泄露通报；同时需评估 TapTap / Phigros ToS 对凭据共享的约束。
- **事故响应预案**：检测到泄露 → 触发 D5 全局 Kill Switch → 通告 → 复盘。

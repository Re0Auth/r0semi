# r0semi / Re0Auth 定位（v1）

> 状态：已定稿。本文回答"这是什么、为谁、不做什么"。
> 技术契约见 [architecture.md](./architecture.md)、[account-model.md](./account-model.md)、
> [api-design.md](./api-design.md)、[upstream-protocol.md](./upstream-protocol.md)。

## 0. 一句话定位

> **Re0Auth 是音游数据的授权与互通层：一套协议 + 一个参考实现。**
> 玩家一次授权，下游一次接入，即可跨游戏、跨数据源读取数据；游戏后端通过实现协议接入生态。

它不是"又一个查分网站"，而是**音游数据域的 OAuth**——定义契约，并给出一个可直接使用、可自托管的参考实现。

## 1. 要解决的问题

| 角色 | 今天的处境 |
|---|---|
| **玩家** | 每个下游工具都索要一次长效凭据（TapTap stoken）；它长效、不可撤销、泄露即失号；玩家无法看到"谁在用、用了什么" |
| **下游开发者** | 每个游戏、每个后端都要单独对接；auth 方式不同、字段命名不同、上游一改就崩；还得自己保管玩家凭据 |
| **游戏后端** | 想被下游接入，就得自己造一套授权系统，否则下游只能要凭据 |
| **生态** | 数据碎片化、凭据满天飞、无法审计、无法撤销 |

三方的痛是同一个：**缺少一层中立的、标准化的授权与数据契约。**

## 2. 定位：标准 + 参考实现

| | 内容 |
|---|---|
| **协议** | 上游契约（OAuth 2.0 profile + 数据 API）与下游契约（OAuth 2.0 授权服务器 + 数据 API） |
| **参考实现** | 本仓库（`internal/*`） |
| **类比** | 就如 OAuth / OpenID 之于身份，Re0Auth 之于音游数据 |

## 3. 三个角色 + 一个运营者

```
玩家 ──外部 IdP 登录──> Re0Auth ──OAuth 客户端──> 数据源（游戏后端）
下游 ──OAuth 授权──> Re0Auth ──归一化 / 透传──> 数据
```

| 角色 | 做什么 |
|---|---|
| **玩家** | 用 GitHub/Google/Discord/QQ/微软 登录，按需绑定各数据源，随时查看与撤销 |
| **下游开发者** | 接入 Re0Auth 一次，拿 Access Token，读归一化或原始数据 |
| **数据源（上游后端）** | 实现上游契约，**对外暴露** OAuth 2.0 授权服务器面（自研 / 现成库 / Kit 生成）+ 数据提供方 |
| **运营者**（可选） | 自托管，或运营公共实例 |

**关键边界：Re0Auth 不直接对接 TapTap。** TapTap 是数据源自己要处理的地基；Re0Auth 只跟"实现了上游契约的后端"打交道。

**"上游支持 OAuth 2.0"的准确含义**：数据源必须**对外暴露**一个 OAuth 2.0 授权服务器面，而**不是**"原生就是 OAuth 2.0"。
前端在数据源侧的登录方式（TapTap 设备码、账号密码…）由数据源自行处理；AS 面可自研、用现成库、或由 Upstream Kit 生成。
判据与反例见 [upstream-protocol.md](./upstream-protocol.md) §3。

## 4. 价值主张

- **对玩家**：一次登录、按需绑定、随时撤销；不再反复交出万能钥匙；始终能看到"谁在用、用了哪个源"。
- **对下游**：一套 schema、一套授权；换源对下游无感（但永远可见 provenance）；永远拿不到上游凭据。
- **对数据源**：实现一次契约，接入整个下游生态；不必自造授权系统。
- **对生态**：数据可互通、可审计、可撤销；多源并存，单源失效不致生态崩塌。

## 5. 明确不做（非目标）

- 不做游戏成绩的**权威主库**；我们聚合与转译，不取代数据源。
- 不修改上游数据（`raw` 模式下逐字透传）。
- 不自建邮箱/密码/Passkey 账号体系（身份交给外部 IdP）。
- 不承诺"永不存储任何东西"——按数据源能力分档，**诚实标注**（见 §8）。
- 不做通用 OAuth 平台；聚焦音游数据域。

## 6. 双边冷启动策略

标准需要两边都到场。破局顺序：

1. **先有参考数据源**：`referencesource`（+ `cmd/referencesource`）已是第一个**独立参考源**——
   用 Upstream Kit 组装，自带 OAuth 2.0 AS 面；登录可配 **TapTap 扫码** 或 **Google/GitHub 社交 OAuth**
   （凭据存进源自己的 vault、身份写入源自己的会话），藏在 `Login` / `Authenticator` 接缝后。
   切片 1–4 已完成（与 `federation` 的绑定/取数端到端 + conformance）；它非 OAuth 2.0 原生，
   且登录本身又可以是 OAuth——两个方向都检验了 Kit 的 `Consent` 接缝。
2. **Upstream Kit 把适配成本压到接近零**：后端装一个组件、填几个 hook，即成为合规数据源。没有这一步，"标准化"只是 PPT。
3. **自己先当第一个下游**：做一个官方查分器 / Bot，证明数据层价值，再开放协议。
4. **优先级**：参考实现可用 > 文档与一致性测试 > 治理形式化。

## 7. 治理与版本

- **协议版本独立于实现版本**（`re0auth_upstream_version`），加法演进；破坏性变更走新 major + 过渡期。
- **一致性测试套件（conformance suite）** 随 Kit 发布；数据源必须通过才能宣称兼容。
- **数据源注册表**：每个游戏的数据源清单、能力、状态（active / degraded / retired）。
- **弃用**：`Deprecation` + `Sunset` 头 + 变更公告渠道。

## 8. 诚实的安全定位

Re0Auth 存的是"**能换到数据的东西**"。它的性质取决于数据源：

| 数据源能力 | Re0Auth 存什么 | 对外可宣称 |
|---|---|---|
| 可撤销、有 scope、可续期（标准 OAuth refresh token） | 可撤销的授权 | **"我们只存可随时吊销的授权，不存你的密码"** |
| 不可撤销、长效（如 TapTap `sessionToken`） | 长效凭据（信封加密） | **"该数据源仅提供长效凭据，我们如实标注并按高危处理"** |

**绝不对所有上游统一宣称"我们不存储凭据"。** 按数据源分类标注，是这套体系可信的基础。

## 9. 主要风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **采用风险（最大）** | 标准需要被采纳，而两边都还几乎为零 | Upstream Kit + 自建第一个下游 + 一致性测试 |
| **平台依赖** | TapTap 等底层平台的封堵 | 由数据源承担与适配；Re0Auth 不直接对接，且**多源**结构上对冲单源失效 |
| **治理缺失** | 没有 spec 治理会退化成各家方言 | 版本规则 + conformance + 注册表 |
| **运营责任** | 公共实例托管全社区授权 = 无限责任 | **自托管是官方支持的选项**；公共实例明确责任边界 |

# ADR-0006：运维边界——备份、保留、KMS 与追踪

> 状态：**已接受**。
> 背景：审计把 Re0Auth 从“功能是否对”推进到“出了事能不能恢复”。本文记录
> 备份/RPO、数据保留、密钥管理与追踪的取舍，以及哪些是明确不做而不是还没做。
> 相关：[threat-model.md](./threat-model.md)、[dependencies.md](./dependencies.md) §3。

## 决策

1. **备份是部署方的责任，仓库提供工具与演练流程。**
   `scripts/backup.sh` 用 `pg_dump -Fc` 产出可校验的转储（可选 age 加密）；
   `scripts/restore.sh` 只允许恢复到空库，拒绝在已有表的库上覆盖。RPO 由备份频率决定，
   建议 ≤ 15 分钟（WAL 归档可做到接近 0）；RTO 目标是 1 小时以内。
   **每次发布前至少做一次恢复演练**：恢复到 scratch 库、指向它启动、检查 `/readyz` 与一次登录。
   数据库之外，`scripts/backup-keys.sh` 备份四把不可重建的密钥（KEK / OIDC 签名 / OIDC 令牌 /
   审计链）；密钥必须存在数据库备份够不到的另一处，否则一次凭据泄露会同时拿走密文与钥匙。
   仓库另附一个**可选**的集群内工作负载 `deploy/k8s/backup/`（每 15 分钟 `pg_dump` + 保留
   7 天 + `concurrencyPolicy: Forbid`），让 RPO 目标默认可执行而不是一句建议；**异地复制与
   加密仍是部署决策**（卷不是异地，转储默认不加密），见 [operations.md](./operations.md)。
2. **审计记录默认无限期保留，且不做行级删除。**
   `audit_events` 是哈希链，删中间行会破坏链验证；账号抹除用的是主体假名化 + 销毁密钥
   （ADR-0005 相关实现），不是删除。需要缩短保留期时，正确做法是归档整段（含链锚）后
   连带锚点一起删除，而不是逐行裁剪；这属于部署策略，不是默认行为。
   运行日志与指标按部署方的日志系统保留策略处理，本服务不持久化它们。
3. **KMS 厂商适配器不内置，`KeyWrapper` 是接缝，不是实现。**
   本地 `LocalKeyWrapper` 是唯一实现；云 KMS/HSM 要按部署引入，并保留自托管回退。
   换来的能力是**可恢复性与可归因**（KEK 不在进程里、解封可审计、密钥可停用），
   **不是防止被攻破的进程解密**——被攻破的进程可以用自己的身份调用 KMS。
4. **追踪只在进程内相关，不导出。**
   服务解析/生成 W3C `traceparent`，把 trace id 写入访问日志，便于跨日志定位；
   不引入 OTel exporter、不上报 span。理由：当前报警与排查靠 Prometheus + 结构化日志，
   在指标/日志/审计三者统一关联方案确定之前，接入 exporter 只是增加一个需要运维的面。
5. **按身份限流不默认开启。**
   limiter 按**（平面, 客户端地址）**分桶，`RateLimit-*` 头已发布。分平面是有意的：一个地址背后
   常常是一整群人（NAT / 办公出口），而两类流量的用途与代价都不同——业务面的读洪峰不该花掉同一
   地址登录所需的预算（实测：用单桶时，一次 `/v1` 洪水会让同地址的 `/oauth/token` 收到 429）。
   代价是每个地址每平面各一个桶，可花总量因此是配置速率的**平面数倍**——一个操作者已经选定的
   数字的有界倍数，而不是无界的。
   按 **client/user** 分桶仍不开启：需要先明确配额归属与套餐模型；在那之前开启会误伤 NAT 后的
   多租户。ADR-0005 记录的 `server.max_in_flight` 是并发的硬上限，与配额无关；该上限在全局之外另给每个**客户端地址**一份**份额**（上限的一半，跨平面合并计算），其余是公共余量——否则单个地址用几个慢 body socket 就能占满全部槽位，让其他客户端全 503 而探针全绿，故障对编排器不可见。份额按地址而非按（平面, 地址）计数：信号量是进程级的，按平面计数会让一个地址用两个平面各占一半、合计吃掉整个上限（第九轮 S10-1）。
   仍开放的一点：桶在**进程内**，N 个副本等于 N 倍限额；换成共享存储是一次部署决策，与"要不要
   按身份限流"是两件事。
   **桶键必须不是调用方能写的值**（第五轮 P0-4）：对端地址，或**声明过的**头的最右侧一条，
   二者都不是调用方能决定的。因此规则是「`trusted_proxies` 说谁有权替客户端说话，
   `client_addr_header` 说那个代理写的是哪个头」，**缺一不可**——只有信任列表时读头，
   在「代理逐字转发调用方自带的 XFF」（nginx 默认）与「追加的那一跳也在信任网内」
   （SNAT / 网格 / 内部 LB）两种常见形态下都会返回调用方写下的地址。前者无法从请求里识别，
   所以默认**不读任何头**；后者的答案是退回对端地址（更粗，但真实）。
   桶表满时**不淘汰活桶**：新键共用一个兜底桶，否则「换一个键」就等于「拿一份新配额」。
   运维侧的要求与实测方法见 [operations.md](./operations.md#反向代理的要求限流分桶键)。
    IPv6 客户端地址按 **/64 归并**（不是 /128）：一个 /64 是单个用户的常规分配，按 /128 计则
    一台主机可用 2^64 个键把桶表填满，之后所有**新**客户端共用一个被排空的兜底桶，形成一次
    匿名 DoS。代价与兜底桶的方向一致：同一 /64 内的主机共享一份预算（更宽的分配接受同样的共享）。
6. **内存模式不提供生产运维保证。**
   没有持久会话索引、没有增量备份、重启即丢失 OP 状态；它用于开发与联调，
   生产必须配置 Postgres 与审计 key。
7. **审计链的串行化：先量化，再决定动不动它。**
   每条审计记录都要锁 `audit_chain` 的同一行（`FOR UPDATE`），而这条写入在数据面的关键路径上：
   `vault.Use` 在交出凭据**之前**先落审计（不变量 I3）。于是全集群的审计写入是串行的，每一次
   带凭据的读取都要过一次这个锁。这是设计（两个并发插入会分叉链），但"它是不是瓶颈"只能靠
   测量回答，所以本次**只加测量，不改语义**：指标 `re0auth_audit_append_duration_seconds`
   （含等锁；面板 “Audit append duration”），加一对基准
   （`TEST_DATABASE_URL=… go test -run '^$' -bench BenchmarkAuditAppend -benchtime 2s ./internal/store/postgres/`，
   无数据库时跳过；CI 在带 Postgres 的作业里跑并打印数字）。
   **判据**：并行基准的 ns/op 不再优于串行，就是拐点——从那里起加连接、加副本都不再有用，
   要谈的是分片链（按 subject 分片 / 异步批量 / 独立审计库），而它们都会改动 I3 的语义，
   必须另开一次决策，而不是在"感觉慢了"的时候顺手改。
8. **上游响应体预算在全局之外另给每个调用方一份份额。**
   `server.max_upstream_buffer_bytes`（`internal/federation` 的 `bufferBudget`，出厂 64 MiB）按字节限制
   两条数据面读取路径同时持有的上游响应体，不变量是 `held <= max_upstream_buffer_bytes`。但只有全局预算时
   它是**先到先得**：一个源 flush 了响应头就停下不发正文，读取方的预留（最坏 `maxBody`，4 MiB）也已经记在
   账上，于是同一个 subject 的十五个这种"零字节读取"就能吃满 64 MiB，把**其他用户**正在进行的整容量读取挤成
   503——攻击成本是十五个 socket 和一个令牌（第七轮 Z09-4）。这与决策 5 里 `max_in_flight` 的道理相同：全局
   上限之外必须再给每个调用方一份份额，否则单个调用方就能占满全部资源，而故障对其他客户端与探针都不可见。
   因此每个调用方（键为 **subject**）最多持有 `max(2*maxBody, max_upstream_buffer_bytes/4)`：出厂默认下是
   `max(8 MiB, 16 MiB) = 16 MiB`，即四次最坏情形读取，其余是所有调用方共享的余量。超过自己份额的读取以
   **同一个** `ErrBufferBudget`（`temporarily_unavailable` + `Retry-After: 1`）被拒绝，而不是去花别人的余量；
   全局不变量和容量公式不变，见 [capacity-planning.md](./capacity-planning.md) §4。按 subject 而不是按对端地址
   分桶，是因为两条读取路径上 subject 一定存在（绑定查询已经用到它），也正好是"凭据属于谁"的键；份额小于两次
   最坏读取没有意义，所以取下限 `2*maxBody`（预算本身低于该下限时全局上限先起作用，小预算仍是全局先到先得）。
   份额表只保存**当前持有字节**的调用方、归零即删，因此其条目数被预算本身限制。

## 已知残余风险（明确接受，不再当作待办）

- **跨实例 binding 刷新竞态**：CAS 已保证单个绑定不被并发刷新两次，但两个实例在
  “赢家落库前同时判定凭据失效”时仍可能重复去上游刷新一次；彻底消除需要 lease，
  当前接受并在 architecture.md 记录。
- **`scs.Store` 接口不带 context**：Postgres 会话适配器因此使用 `context.Background`，
  请求取消无法传播到会话读写；这是上游接口的限制。
- **审计链无法检测尾部截断**：链能发现中间篡改，不能发现删除最后一行。已提供
  `GET /v1/admin/audit/head` 暴露链头，供外部系统发布到不可由数据库账号改写的位置；
  不发布该链头的部署，仍然只有原有的较弱保证。
- **sweep 与锚点循环每个副本都跑一遍**：两者都幂等（过期行删除、链头重复记录），代价是重复的
  写负载与同一时刻的多条锚点日志行。收敛到一个执行者需要 leader 选举或把循环改成 CronJob，
  当前接受。

## 后果

- 发布流水线之外，运维需要备份作业与季度恢复演练；没有演练的备份不视为可用。
- 想缩短审计保留期的部署必须自己实现归档 + 锚点删除，不能 `DELETE FROM audit_events`。
- 引入 OTel 或云 KMS 时先写新 ADR，不要直接改这里的结论。

## 测试/演练锚点

- `scripts/backup.sh` + `scripts/restore.sh` 的恢复演练（每季度一次，记录结果）。
- `internal/httpapi` 的 `/readyz` 依赖失败测试、`server.max_in_flight` 的 503 形状测试、
  `RateLimit-*` 头测试与 `traceparent` 解析测试。
- `internal/archtest` 对 `deploy/k8s` 的探针、资源上限与 securityContext 断言。
